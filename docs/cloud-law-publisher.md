# Cloud legal publisher

This procedure is invoked by the ChatGPT cloud task on the 1st and 15th at 08:41 Asia/Beirut. It replaces the credential-dependent GitHub research cron; GitHub Actions remains the only production publisher. News research is owned by its separate existing cloud task.

1. Use the configured cloud environment and fetch the latest `origin/main`. Never use desktop files or accumulated chat memory. Require `.github/workflows/law-update.yml` to accept `automation/legal-release/**`; otherwise stop and report the missing rollout. Check the Beirut date and `updates/state/law.json`; run only on the 1st or 15th from 08:41 onward and skip a date already successfully completed. Accept delayed starts later that day.
2. Check GitHub Actions for active publication and existing unmerged legal release branches. Do not duplicate an active release. Create `automation/legal-release/YYYY-MM-DD-<unique>` from current main. Read the current schemas, `scripts/auto-publish.ts`, critical-source policy, scope policy, current legal records and source registers before preparing evidence.
3. Research with the cloud agent's direct browsing and source retrieval. Do not call `npm run update:laws`, an external model API, or repository AI credentials. Cover Lebanese energy law, policy, regulation, standards, petroleum and institutions. Retrieve controlling official primary texts and relevant discovery indexes. Preserve the exact cutoff, retrieval results, source locators and bounded coverage window required by the repository. Record unavailable sources, rejected candidates and uncertainty. Never invent successful retrievals, legal status, translations or verification flags. Inadequate controlling evidence means rejection or a failed run, never an assertion of no changes.
4. Produce the schema-compatible files `updates/research/law-evidence.json`, `updates/candidates/law.json`, `updates/candidates/law-verification.json`, `updates/candidates/law.md` and `updates/pending-state/law.json`. Keep actual retrieved text and cutoff timestamps aligned. Candidates require controlling primary sources, High confidence, amendment and implementation checks, article/page locators, separate publication/effective dates, bilingual professional detail, source-backed relationships, provenance, supersession and correction history. A fully researched, validated zero-candidate result is acceptable.
5. Run `npx tsx scripts/check-critical-sources.ts --mode law`, `npx tsx scripts/auto-publish.ts --mode law`, `npx tsx scripts/check-update-scope.ts --mode law --base origin/main`, `npm run validate:content`, `npm test`, `npm audit --omit=dev --audit-level=high`, and `npm run build`. Never bypass or weaken gates. Do not edit code, workflows, news files or promoted state. Only the law allowlist and integrator-generated publication ledger/marker may change. Confirm any shared publication-ledger change preserves all news entries.
6. Fetch main again before pushing. If it moved, restart integration and validation against the new revision instead of force pushing or overwriting it. Commit only allowed files with a gitmoji shortcode message and push the unique release branch. Never push directly to main, and never open a parallel release when one is active.
7. Follow `Publish verified legal framework changes` through source scope validation, complete build, immutable deployment, exact-marker smoke test, state promotion and main fast-forward. GitHub Actions serializes production publications and rolls back after post-deployment failures. Do not manually promote pending state or mark a release successful before the workflow completes.
8. Notify on completed publications, failures, rollbacks or required user action with the research cutoff, coverage, checked sources, accepted/rejected counts and workflow link. Remain quiet after a validated unchanged no-op. Missing cloud or connector access is a blocker to report, not a reason to fabricate success or use desktop execution.
